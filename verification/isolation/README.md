# Isolated transfer refusals

This separate corpus executes the same pinned Solana artifacts with a fresh task-authored observer. A deposit, approval, small transfer and same-module SetPolicy rebind leave genuine spending headroom when the switched policy's standing approval is tested. Reapproval and valid transfers supply positive VM witnesses. Wrong executor, unsigned executor, stale revision and replay are then tested independently. There are 12 recorded executions: seven successes and five refusals.

For each transfer, Python checks 11 non-environment prerequisites from the independent state specification: signer flag, executor identity, current revision, fresh nonce, approval, positive amount, bounded limit, non-regressing day, spending headroom, nonce capacity and funding. Two generic Lean theorems prove that all entries hold exactly when the specified model transfer prerequisites hold and exactly when a successful transfer exists with readiness True. Each targeted refusal has exactly one false entry. Lean checks that complete Boolean vector, proves no successful transition for any readiness predicate/post-state, and proves a positive counterfactual after repairing the one named condition with readiness set to `True`. Seven successful-state certificates and four Lean-rechecked arithmetic transcriptions of Python-decoded balance deltas bring the total to 28 checked statements.

The counterfactuals are model witnesses, not authority grants, reachable owner approvals or proofs of real repaired execution. Separate actual successes are recorded without claiming an exact intervention correspondence. Signer flags and time are harness inputs, not real signatures or independently decoded chain time. Readiness includes platform/account/artifact/token prerequisites not discharged by these 11 checks. Exact-next is an existential output constraint checked in each successful/repair proof, not an omitted independent authorization predicate.

Observed raw account/state continuity is checked across all 12 executions as observer bookkeeping; Mollusk is fed the preceding returned accounts rather than proving persistent chain storage. Python checks that the sum of the three fixture token balances equals mint supply; account identity and supply are not formal Lean token-account proofs. The initial custody state is constructed by the fixture, not a verified initialization. No universal execution trace, platform completeness, production error cause/precedence, runtime rollback, program build provenance, clients or deployment is proved. Mollusk failure-result equality still follows its input-account-return convention.

The observer reuses the pinned historical recording-helper prefix, moving only its dead-code lint attribute to the new crate root. Fixture reuse copies the exact committed test-helper prefix and changes only its source-hash module path. Both are assembly for an isolated harness, not semantic Rust extraction. Production sources, earlier corpora, models and receipts stay unchanged. The trusted Python entry-point hashes all listed nonstandard Python dependency bytes before loading them through compile/exec from the verified snapshot; those dependency modules do not use cached bytecode. This covers the explicitly listed modules, not a mechanically enforced transitive import closure. Standard Python execution and the dependency import graph remain trusted; lazy imports are not separately attested. Disk drift is checked afterward. The exact source/tool/library/cache/artifact pins are inherited from the historical trace lock and checked before/after acceptance; cached build fidelity, linking, observation/decoding, Lean/core and VM semantics retain their trust boundaries.

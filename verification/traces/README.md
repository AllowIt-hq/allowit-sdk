# Finite custody trace correspondence

The isolated Rust harness executes the pinned Solana custody and policy SBF artifacts in Mollusk, records request bytes/account metas and before/after custody and token projections, then generates Lean certificates against the unchanged independent [state specification](../adapter/State.lean). Thirty-two certificates check 13 successful transitions, five source/recipient balance effects, 13 rejected-state equalities and one diagnostic exact-wrap/mismatch conjunction.

This is **finite compiled adapter projection correspondence**, not universal Rust/SBF refinement. It does not discharge the platform `ready` predicate: successful projection certificates instantiate it with `True`, and actual signing keys, cryptographic verification, arbitrary accounts, network inclusion and deployment identity remain outside this harness. Actor identity/signature flags come from supplied VM account metas. They test custody's handling of those flags, not real wallet signatures.

## Cases and observations

The 26 ordinary cases cover deposits/top-up, approval/reapproval/revocation, successful spending, duplicate nonce, bounded tuning below spent/zero/resume/max, same-day refusal, next-day exact limit, in-place policy switching, owner withdrawal, wrong/unsigned executor, stale revision, unsupported methods, counter/revision overflow and resource-failure returned-state behavior. Explicit expected error codes and distinguishing failing preconditions are checked; these are not necessarily single-fault witnesses. In particular, `switch_revoked` also exceeds the daily limit, so it does not establish refusal caused solely by revocation. These are a corpus of instruction executions, not a single reachable initialization trace: the fixture starts with constructed custody state, and overflow cases deliberately inject counter values. Initialization/factory refinement and continuity of an initialized reachable trace are unproved.

For the budget-exhaustion case, the normalized VM log shows token CPI invoked and succeeding before custody fails with `UnknownError(ProgramFailedToComplete)`. The harness compares **every returned input account** with its actual before-account and derives the after projection from those returned accounts. The inspected pinned Mollusk `harness/src/lib.rs` explicitly uses `accounts.to_vec()` on error ([upstream revision](https://github.com/anza-xyz/mollusk/blob/f432ef136ee9779d2a814ebf2b80f44c10607255/harness/src/lib.rs)). Thus the rejection certificates establish equality of the VM API’s returned projections; preservation follows from its failure-result convention and cannot demonstrate custody rollback or hidden intermediate execution state. This is one concrete VM failure-result witness, not a universal rollback theorem or a statement about transaction fees.

Failure can leave return data that encodes an intermediate state while Mollusk returns the input accounts. The trusted Rust observer decodes and asserts the intermediate nonce/spent values; the budget case retains those bytes. callers must determine execution from the finalized transaction/account outcome, not a failed instruction's returned state. SDK/gateway/client handling of that distinction still needs its own evidence.

The diagnostic `injected_supply_violation` sets the recipient balance to `u64::MAX` while other accounts still hold tokens. The observed token execution accepts the transfer and wraps the recipient to zero. The three fixture token balances then exceed the mint supply; this is an explicitly injected invalid supply state, not a production exploit or a reachable-ledger claim. Its retained Lean certificate proves the observed recipient equals the modulo-2^64 sum and differs from exact integer addition. The diagnostic additionally checks the exact custody balance/nonce/spent effect. The 26 ordinary cases instead require the three fixture token balances to sum to the mint supply before and after; this is a fixture check, not a proof of the entire chain's token invariants. Invalid supply inputs are never included in ordinary permission correspondence.

The token ELF embedded by the cached dependency reports 108,600 bytes and SHA-256 `8190d3f7ceb6cb7a7a8d8924bff89f9f611e15ce1f806f2b6237f3311a98f697`, matching bytes independently downloaded from the [pinned upstream Mollusk file](https://raw.githubusercontent.com/anza-xyz/mollusk/f432ef136ee9779d2a814ebf2b80f44c10607255/programs/token/src/elf/token.so). That byte comparison does not prove the cached runtime/dependency libraries were faithfully built from their source or that their VM matches a deployed validator. The cause/production reachability of the diagnostic is not proved here.

## Run and boundaries

```sh
PYTHONPYCACHEPREFIX="$(mktemp -d /tmp/allowit-extraction-oct05/python-cache.XXXXXX)" python3 verification/traces/check.py --tools /tmp/allowit-extraction-oct05
PYTHONPYCACHEPREFIX=/tmp/allowit-proof-python-cache python3 -m unittest discover -s verification/tests -v
```

Run acceptance with a fresh Python bytecode-cache directory as above; import/cache fidelity is otherwise part of the trusted observer boundary. The checker compiles the task-authored harness freshly with pinned host Rust 1.98 and cached dependencies. It reads the fixture-helper prefix from the exact committed contract test source and changes only its module path to an isolated copied source-hash file. The helper creates synthetic VM accounts; the task harness itself constructs and passes the exact captured instruction directly to Mollusk. this extraction is fixture reuse, not Charon/Aeneas semantic extraction. The new harness adjusts the mint supply to match its ordinary fixture balances. Production implementations, tests, artifacts and global caches are never modified.

Pins include the source/fixture bytes, parser/certificate builder, independent models, published intake, compiler binary and every compiler-library file, 719 cached dependency artifacts, Lean binary/core libraries, direct extern selection and the contract artifacts. Only the explicitly trusted cached dependencies are linked; no Cargo build, installation or download occurs during acceptance. Native linking and system runtime remain trusted. Acceptance is tied to this pinned arm64 macOS host and dependency cache; two fresh temporary-directory runs have reproduced native executable identity. The fresh harness executable identity is recorded and checked around execution. Fresh request/state corpus, normalized runtime events, generated certificate bytes and proof log must match retained evidence and receipt exactly; inputs are checked again afterward. Candidate refresh uses `--emit-receipt --emit-evidence` into the isolated tool root, followed by explicit review.

The Borsh decoder here is an independent fixed-layout parser for the corpus's delivered custody methods. It refuses malformed lengths/tags/booleans. It is not a universal codec proof. It maps canonical 32-byte hex identities to natural numbers and u64 scalars to `Fin`; the successful certificates check the entire model state projection and separately declared asset deltas. ABI/bump/token-account/vault-ID/mint metadata must remain unchanged. Raw before/returned account images are retained. An independent Python fixed-offset custody/token/mint decoder cross-checks the shared cached interface decoder. Source and recipient account identities are bound to the instruction metas. The five projected account keys must be distinct; all token mints match the asset, vault token authority matches custody and source token authority matches the owner. Successes check owner/lamports/executable frames, token non-amount bytes, custody trailing bytes, unrelated accounts and external balance frames; omitted account fields remain outside this projection. The Python interpreter/decoder and Rust observer are trusted, not formally refined. The distinguishing preconditions of each refusal are checked separately from shared error codes. Rejection certificates do not prove that the independent successful-transition model refuses the 12 policy-rejected requests; that separate obligation remains open. Budget exhaustion is a `ready`/environment failure and is excluded: the model with `ready := True` permits that request. Earlier model axioms were audited in the preserved adapter receipt, while this checker audits the fresh certificate closure.

All 24 release obligations remain open. This supplies finite partial evidence for V05–V13/V23/V24. Stellar compiled traces, authenticated real signatures, malformed custody/account/loader cases, general readiness, arbitrary concurrency, universal rollback, rebuilt program provenance, connected SDK/gateway/CLI/frontend behavior and deployed identity remain unproved. The earlier kernel/model/VM receipts are preserved as their original evidence.

# Retained transaction frame proofs

[Frame.lean](Frame.lean) independently defines a finite store of symbolic account identities and fingerprints. A failure before execution preserves the entire store and has zero fee in this fixture profile. An executed abort permits only the separately funded payer debit; the formal relation has no failure-site tags. Locked Python log/outcome checks separately retain the observed later-instruction, token-resource and post-token-resource boundaries. Expected fees are supplied data, not a theorem about Solana's fee calculation. The selected LiteSVM fee profile has no fee collector/rent-exemption model. Durable nonce transactions and fee-payer/custody aliasing are refused by the selected bindings. Existence means only a funded unique model store, not platform readiness.

Ten generic statements prove key inventory, protected projection and zero-debit preservation; failure frames; pre-execution zero effects; abort/fee-frame equivalence; existence for every unique funded store; and exact debit arithmetic under sufficient funding. These follow from the independently stated relation. They are not universal runtime rollback theorems.

[Corpus.lean](Corpus.lean) is generated from the unchanged retained transaction and failure-boundary corpora. Its 16 finite certificates comprise seven failure frames, three custody equalities across abort/reuse, three identical-request/state-nonce/revision bindings and three successful reuse transitions; three additional nonce-advance statements are derived corollaries. The successful witnesses use the unchanged handwritten custody specification for an arbitrary readiness predicate with an explicit environment hypothesis. Platform readiness remains unproved. The full custody state includes decoded balance, identity, policy, limit, spending/day, nonce, revision and approval. Token recipient effects remain Python-checked by the existing validators, not new Lean token-transfer proofs.

The store projection contains every one of the 292 enumerated entries: owner identity, lamports, executable flag, rent epoch and opaque data-digest identity. Lean checks these complete finite projected lists, including unique keys and preserved inventory. Absence follows only relative to that trusted enumeration. Digest equality is symbolic; SHA256 collision resistance, raw-byte/fingerprint correspondence, actual complete enumeration and observation authenticity remain trusted. Failure-site classification is outside the formal relation; locked strict Python validation checks instruction/log/account evidence. Lean does not prove an instruction prefix, intermediate balance, token implementation, exact failure cause or stage classification. The generator independently binds raw bytes and metadata to whole-store fingerprints, refuses duplicate raw keys, selects the custody account from the transfer roles, checks layout/padding, binds its program/asset/token/policy/ProgramData accounts, and emits both failed and successful actions. Amount/nonce/revision/signing-position and Clock projections come from retained raw data; actual signature enforcement and Clock/syscall-cache agreement remain runtime assumptions.

## Acceptance

[check.py](check.py) verifies all locked bytes and historical receipt file/test identities. It snapshots the old validators and bindings into a fresh isolated directory, executes their exact verified source bytes, checks both retained replays and normalized digests, regenerates the corpus identically, and compiles NativeDaily, State, Frame and Corpus from source in that fresh directory. It first checks a positive fee-frame control, then requires Lean to reject five false controls (underfunded fee, changed payer metadata, changed protected balance, a single protected-account digest perturbation in the actual retained store, and a wrong nonce against the captured failed request). It audits every theorem in those four files, allows only propext/Quot.sound, screens the listed admission/command constructs, except the unchanged, exact historical NativeDaily `#eval evaluate exampleContext` demonstration. That demonstration executes during compilation and is not used by the proofs. The checker verifies source/tool/library identities again afterward. Duplicate JSON object keys are refused. Snapshot imports have an AST allowlist screen; this is not a sandbox. Acceptance requires an isolated Python interpreter (`-I`) and disabled bytecode writes (`-B`). Isolation keeps the script directory off the import path; verified snapshot modules are compiled from source bytes. The interpreter may still read trusted standard-library caches. Standard Python, transitive standard-library imports, linking and cached official Lean-library build fidelity remain trusted. This is not a hostile-proof acceptance sandbox or an external independent kernel check; see [Lean's validation guidance](https://lean-lang.org/doc/reference/latest/ValidatingProofs/) for the stronger comparator/checker boundary.

```sh
python3 -I -B verification/runtime/frame/check.py --tools /tmp/allowit-extraction-oct05
```

Default acceptance requires the retained receipt to equal the freshly checked result, including Python version and executable hash; a different interpreter fails receipt freshness. Candidate creation uses --emit-receipt; --emit-evidence accepts a directory only under the isolated tool root. Acceptance never installs dependencies, builds Rust or executes a VM. The corpus-generation script is a trusted parser/transcriber; its bytes and regenerated Lean output are pinned. A proof of its own semantic correctness is not supplied. Literal certificates check the described formal projections, conditional on that correspondence.

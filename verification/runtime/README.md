# Transaction rollback acceptance preparation

No signed-transaction/store experiment has run here. A subsequent [finite loader preflight](loader.md) is recorded separately. All 24 release obligations remain open. This is preparation for V06–V08/V12/V23, separate from the retained Mollusk corpora. Initial inspection found no validator executable or cached LiteSVM package; the separate preflight subsequently prepared an isolated LiteSVM build. The [research inventory](research.json) binds inspected source bytes; it is not a build lock or runtime receipt.

Solana's [transaction pipeline](https://solana.com/docs/core/transactions/transaction-pipeline) documents failed-execution account rollback with fee-payer and durable-nonce exceptions. Existing Mollusk instruction and transaction APIs return input accounts on error. Rechecking those returned values cannot observe a rollback in a store that persists across transactions.

A candidate is LiteSVM pinned for **source research only** at [`980f39121cda14bc78d8c46489d2d12fb0cc6eae`](https://github.com/LiteSVM/litesvm/blob/980f39121cda14bc78d8c46489d2d12fb0cc6eae/crates/litesvm/src/lib.rs). Inspected paths in `lib.rs` and [`accounts_db.rs`](https://github.com/LiteSVM/litesvm/blob/980f39121cda14bc78d8c46489d2d12fb0cc6eae/crates/litesvm/src/accounts_db.rs): `sanitize_transaction` verifies signatures; `send_transaction` synchronizes execution accounts only on success; failed execution with a context calls account-store `withdraw` on the payer separately. These are inspected call paths, not an exhaustive absence-of-other-effects theorem. `new()` enables signature/blockhash checks, while `default()` does not. These statements rest on the hashed source, including functions outside the initial reviewer excerpt. This source inspection motivates the test design; it is not evidence that the candidate builds, accepts our artifacts or matches a deployed validator.

## Minimum experiment

Use a new isolated Rust package and dependency/tool cache, with an exact toolchain and resolved Cargo lock. First bind custody/policy/token ELF bytes and loader configuration, feature set, sysvars, transaction limits and runtime source/dependencies. Verify the actual loaded token program bytes, not merely the bundle shipped with `new()`; bind the loader account/ProgramData payload to each expected ELF. Source-to-ELF build provenance remains unestablished. Attempt loading unchanged published programs. Unsupported loader, ISA or syscall behavior yields an explicit unsupported result, never a permissive substitute. Fixture-injected accounts remain constructed state; separately retain any successful constructor/deposit/approval transactions if claiming reachable initialization.

1. Derive fixture keypairs from retained test-only deterministic seeds (never production credentials) and a distinct fee payer outside custody/token accounts. Capture the account pre-image set defined in step 2 before the blockhash control. Enable signature/blockhash checking and read back `get_sigverify()`. Blockhash checking has no public getter without an internal feature at this pin: instead submit a validly signed non-nonce transaction with a different blockhash and require `BlockhashNotFound`, no program logs and no payer/protected-store change. Retain signed transaction bytes and decoded message/account ordering; derive program signer flags from the signed message rather than supplying them to an instruction runner. Capture the authoritative runtime Clock account and decode its timestamp. Pin log capacity (prefer no limit), read back configuration where available, otherwise retain configured arguments and pinned default source; do not enable internal features silently, and reject truncated/missing expected logs as inconclusive. Require pairwise distinct transaction IDs for included submissions; exempt the signature-rejected corrupted copy, which never enters history. Reject `AlreadyProcessed` as an invalid control; retain failure history for included abort transactions.
2. Derive the protected account set from every final-message writable account except the distinct payer; also capture all referenced program/ProgramData/token/mint accounts. Also include every read-only message account and all sysvars used; compare the full captured union, excluding only the payer. Presence is a separate Boolean: absent and present-zero-lamport accounts cannot be collapsed. Record store canonicalization/pruning as an observability limit; do not claim distinctions the runtime cannot expose. Read complete images (lamports, owner, executable, rent epoch and data, including absence for not-yet-created accounts) from the persistent runtime store. Submit one valid transfer as a signed transaction. Require successful custody and token CPI execution, exact accounting/nonce/day and independently decoded source/recipient deltas. Read the store again. This positive control rules out a store that never commits. Also submit two sequential valid transfer instructions in one transaction with consecutive nonces and require both exact effects to commit; a runtime that drops every multi-instruction transaction cannot satisfy this control.
3. Submit a **new signed transaction containing two instructions**: a valid transfer with the current nonce/revision, then the published custody `Unsupported` variant. The published dispatch refuses this variant. Require logs showing the first custody instruction and token CPI succeeding, then the second instruction failing; pin its exact failure index/error against the final message layout (compute-budget instructions can shift the index). Pin compute limits through explicitly captured ComputeBudget instructions and retain consumed units; fund the payer sufficiently so fee debit cannot mask the instruction error. Read protected accounts directly from the same runtime store; require byte equality with their pre-transaction images. No store/context mutation by the harness may intervene: no account restoration, `set_account`, `set_sysvar`, clock warp, airdrop, program replacement or blockhash advance/expiry. Compare every captured field and account absence; no newly created message account may persist. Require a fresh transfer-only transaction with the identical transfer instruction immediately after the abort to succeed with exact deltas from that same pre-image, showing the nonce/revision remains usable. Logs and failure index remain trusted observations of prefix execution, not independently exposed intermediate state. This establishes a finite transaction-abort witness even if a compute-budget failure cannot be reproduced.
4. Check the payer separately against recorded fee metadata and configured fee rules (the pinned `FeeStructure::default()` when no internal setter is enabled; compute-unit price fixed at zero or explicitly included). Use recent blockhash transactions in this minimum experiment; durable nonce is explicitly excluded. Retain the transaction outcome/history entry when the pinned runtime exposes it, and account-store observations. The same runtime's bookkeeping remains trusted. Freeze the captured Clock and blockhash across each pre/submission/post/control window; read back their identities rather than silently warping them.
5. Create a freshly signed never-submitted transfer using current nonce/revision and a valid blockhash; retain it before submitting a copy with the custody-authorizing executor signature corrupted at its decoded non-payer signer index; retain that index and signer identity. Require the exact signature-failure error, no program logs and no protected-state or payer changes. Then submit the uncorrupted original and require exact successful effects; stale nonce/history/blockhash rejection cannot satisfy this control. This tests runtime signature enforcement; it is neither a proof of cryptography nor an owner-approval theorem.

The second-instruction abort demonstrates rollback after a previously successful instruction, not failure inside the custody transfer. A later experiment must independently show a token CPI success followed by failure of that same custody instruction (the historical budget trace supplies a candidate, not a guaranteed threshold for another runtime). A token-call failure before mutation is a different boundary. Keep all three cases separate.

## Connection to Lean

Use a separately written strict decoder, rather than the production interface crate, to decode the successful transfer into the independent `State.Transition` relation, retaining the runtime readiness assumptions and exact account/units mapping. The failed two-instruction transaction needs a transaction-level relation: successful instruction prefix plus abort with a protected-store frame and declared fee effect. The existing successful-transition specification does not define this relation. Do not pretend that a model refusal certificate proves rollback.

Lean can check finite decoded account/frame arithmetic and a separately specified transaction relation. It cannot authenticate observation, prove translator/runtime fidelity, establish production build provenance or infer universal readiness from this experiment. A local validator run and public deployment reconciliation remain separate evidence domains. Retain raw transaction, logs, before/after store images, decoder output, binary/source identities and rejection controls; rerun in fresh roots before accepting a new receipt.
